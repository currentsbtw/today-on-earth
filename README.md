# Today On Earth

Today On Earth is a news heatmap with no editorial voice: a flat world map that glows where the world's press is writing about something, built from GDELT's free 15-minute Global Knowledge Graph feed. An ingest job (`ingest/`, Node 24 + TypeScript) keeps a rolling 24-hour window of geocoded articles, bins them into H3 resolution-3 cells, and writes the static JSON files described in `docs/DATA-CONTRACT.md` (`heat.json`, `cells/<id>.json`, `history/`); the static site (`web/`) reads only those files. To run the ingest locally: `cd ingest && npm install && npm run ingest` (writes to `ingest/out`; set `COLD_START_HOURS=1` for a quick first run, `OUT_DIR=../web/public/data` to feed the local site, `CARRY_DIR` to keep the carried `state.json.gz` and `history.json.gz` somewhere other than `OUT_DIR`, and `npm test` / `npm run check` to run the unit tests and validate the output against the contract). The local-language place names that confirm the top stories (`ingest/data/placenames.json`, from GeoNames, CC BY 4.0) are refreshed by hand about monthly with `cd ingest && npm run placenames -- --state <carry dir or state.json.gz>` (it downloads the GeoNames dumps unless `--geonames <dir>` points at extracted ones) and committed. To run the site: `cd web && npm install && npm run dev`. To deploy on GitHub: make the repository public (scheduled Actions minutes are free there) and set Settings → Pages → Source to "GitHub Actions". A repository variable `SITE_URL` (the site's base URL, for example `https://<user>.github.io/today-on-earth`) is optional and only informational; the workflow does not read it. The `Snapshot` workflow runs every 15 minutes and deploys the rebuilt site.

Place pages: `npm run build` first runs `web/scripts/build-places.mjs` (the `prebuild` step), which reads the snapshot in `web/public/data` and writes a static page for every place with 10 or more articles (`place/<cell id>.html`, no JavaScript) with an Atom feed of its stories beside it (`place/<cell id>.xml`, linked from the page) and its share image (`place/<cell id>.png`, 1200x630, the page's `og:image`: the world's dots with the place ringed, drawn in Node with no dependency), the index of every place with 2 or more (`places.html`), the day's broadcast as a page (`broadcast.html`, the six signals from `broadcast.json`; six empty slots when the snapshot has none) with its Atom feed (`broadcast.xml`, one entry per UTC day), and `sitemap.xml`, so each deploy carries pages for that snapshot. It writes `404.html` too, which GitHub Pages serves for any missing path: an address under `place/<cell id>` whose page, feed or image is gone (the place dropped out of the window) goes to the map with that cell selected. These files are generated and gitignored; `web/public/robots.txt` (committed) points crawlers at the sitemap. `embed.html` is the map for other sites to frame (no MapLibre; the iframe line is on the about page). Locally the script runs on whatever `npm run predev` or the ingest put in `web/public/data`; a place whose cell file is missing gets no page and an unlinked index row.

Carried state: the rolling window (`state.json.gz`), the replay history (`history.json.gz`) and the per-cell daily counts behind each cell's normal level `b` (`baseline.json.gz`, last 14 days) travel from run to run through the Actions cache in a repo-root `carry/` folder and are never deployed. After each save the workflow deletes all but the 3 newest `carry-*` cache entries (this needs the workflow's `actions: write` permission; a failed prune never fails the snapshot). A carried file that exists but cannot be read fails the run on purpose, and so does a cache miss unless the repository variable `ALLOW_COLD_START` is `true`. For the first run, set `ALLOW_COLD_START=true`; after the first green run, set it to `false` so a cache outage or evicted entry fails the run instead of shrinking the window (to clear the cache on purpose, set it to `true` for one run). A permitted cold start fetches the last 6 hours of GDELT files and begins a new 24-hour replay history (each run appends one compact heat frame to `history/`, at most 100 frames).

Note: GitHub disables scheduled workflows in public repositories after 60 days without repository activity. Push a commit or run the `Snapshot` workflow manually (Actions → Snapshot → Run workflow) at least every two months, or the map stops updating (do not rely on the keepalive below for this).

Keepalive: GitHub's cron is best-effort, so each snapshot run ends with a `keepalive` job that waits a fixed 780 s and then dispatches the next snapshot unless another snapshot run was created after it (any event, any status) or one is already queued or running. It also dispatches the `Clip` workflow once a day after 00:20 UTC if no clip run exists yet that day. Set the repository variable `KEEPALIVE` to `false` to turn it off.

## Rolling back

The carried files (`state.json.gz`, `history.json.gz`, `baseline.json.gz`) have format versions. Newer code reads older files, but older code cannot read newer ones, so deploying an older commit against a cache written by newer code fails every run, on purpose, rather than silently starting over. To roll back: delete the `carry-*` caches (Actions → Caches, or `gh cache delete` for each `carry-*` key), set the repository variable `ALLOW_COLD_START=true` for one run, then set it back to `false`. That run cold-starts the 6-hour window, and the replay history and the baseline start again from empty.

## Daily clip

Every day at 00:20 UTC (after the 00:15 snapshot) the `Clip` workflow renders a vertical newscast of the last 24 hours: a synthetic voice reads a fixed script while the map follows it. The voice reads the opening (the date and the day's totals of articles, outlets and countries), then the day's six largest stories around the world, the first six entries of `data/stories.json` (each one's place, its counts of articles, outlets and languages, and the outlet's own headline when that headline is in English; a headline in another language is shown on screen and the voice says only which language it is in, unless Kokoro has a voice for it), then the close (the broadcast's address and "Read by a synthetic voice from the outlets' own headlines."). Nothing else is spoken, and the outlet is not named aloud: its name on screen and in the caption is the credit. The voice is Kokoro (`kokoro-js` 1.2.1 on ONNX Runtime, model `onnx-community/Kokoro-82M-v1.0-ONNX` in fp32, voice `af_heart`, Apache 2.0), run offline on the runner's CPU; the same text gives the same audio. A headline in Spanish, French, Italian, Portuguese, Hindi, Japanese or Mandarin is read in that language by Kokoro's voice for it (`ef_dora`, `ff_siwis`, `if_sara`, `pf_dora`, `hf_alpha`, `jf_alpha`, `zf_xiaobei`; `VOICE_FOR_LANG` in `render/src/speech.mjs`), with the place said first by `af_heart` and 0.25 s of silence between them in the one line WAV; German and every other language stay on screen. kokoro-js phonemises English only, so those headlines' phonemes come from `render/py/phonemize.py` (the Python front end misaki 0.9.4: espeak-ng from the `espeakng-loader` wheel, cutlet for Japanese, jieba and pypinyin for Mandarin), which `speech.mjs` runs with `uv run --project render/py --locked` in an environment at `render/.cache/py`; it needs [uv](https://docs.astral.sh/uv/) on PATH (it fetches Python 3.12 and the locked packages, about 380 MB, on first use; when it cannot run, fails or takes over 120 s, those headlines fall back to the on-screen line instead of failing the clip, and `KOKORO_PHONEMIZER=none` simulates that), and the workflow installs uv with `astral-sh/setup-uv` and caches its packages. The script's template is `render/src/script.mjs` (the contract is docs/PLAN.md "Clip v4: the newscast"). `render/` builds the script from the live `stories.json` and `heat.json`, synthesises one 24 kHz mono WAV per line (`voice/line-<id>.wav`, measured from its samples) and writes `script.json` with each line's `seconds`; then it loads the live site's `clip.html?newscast=1&w=1080&h=1920&fps=30&max=<n>` once in a headless system Chrome (playwright-core, no browser download), hands the page the script (`window.__clipNewscast(script)`), which returns the plan (the frame count, the clip's UTC day, the poster frame, the segments: the opening, a flight and a card per story, the close; and the start frame of each line), checks the plan, and steps it frame by frame (`window.__clipStep(i)`, one screenshot each). `max` is the live `heat.json`'s largest cell count, read once at the start, so the heat scale cannot jump when a deploy lands mid-clip. ffmpeg mixes the soundtrack (`audio.wav`, 48 kHz mono): each line's WAV placed at its line's start in the plan, over the v3 bed (55/110 Hz sines, here at about -26 dBFS) with a quiet rising glide under each flight, no clicks or blips. The model (about 325 MB) is downloaded from Hugging Face on first use into `render/.cache/kokoro` (gitignored; `KOKORO_CACHE_DIR` overrides it) and cached in Actions; `node src/speech.mjs --self-test` voices one English and one Spanish line to check the setup (the second through uv and the phonemiser). `--script <dir>/script.json` reuses a voiced script (its WAVs in `<dir>/voice/`) and skips the synthesis; `--no-encode` stops before the video encode. The v3 time-lapse clip stays for one release as `--mode timeline` (with `--hook --fly --lapse --card --end --slots --music`, as before). ffmpeg encodes `clip-<YYYY-MM-DD>.mp4` (H.264 yuv420p + AAC 128k, faststart, named after the UTC day the snapshot's window mostly covers) plus `poster.jpg` of the plan's poster frame. `--fps` and `--hold` set the frame rate and the seconds the last frame is held. Download the clip from the workflow run's `clip` artifact (kept 30 days) or from the rolling `clips` release on GitHub, where each day's mp4, caption and `script-<date>.json` are added and `poster.jpg` is replaced. Run it by hand with Actions → Clip → Run workflow (width and height are inputs; both must be even). To render locally against the dev server: `cd web && npm run dev`, then `cd render && npm install && npm run clip -- --site http://localhost:5173 --out ../clip-out` (Edge is used on Windows, Chrome elsewhere; `--channel` overrides; without `ffmpeg` on PATH the frames, poster, script, bed and line WAVs are written, the mix and the encode are skipped and their ffmpeg commands are logged). In CI, ffmpeg is a pinned, checksum-checked static build (ffmpeg 7.0.2) cached across runs, with apt as the fallback, and `npm ci --ignore-scripts` installs `render/` (no install script is needed). A page load that fails is retried once; a frame whose step fails is retried once, and a frame that fails twice is replaced by the previous frame; the run fails once more than 10% of frames are bad, or when the page's plan does not match the contract. Beside each mp4 the renderer writes `caption-<date>.txt`, the text to post with the clip: the date, the signal links the plan carries with their place pages' addresses, the broadcast page's address (a video cannot carry a link, so the caption does), then the transcript: each spoken line, with each story's headline credit under it ("Headline from wamc.org", plus the headline itself when it was shown and not read); the workflow uploads it and `script.json` with the mp4 to the artifact and to the `clips` release. Posting the clip to TikTok is manual.

## Archive

The site and the carried state only hold the last 24 hours, so every successful snapshot is also archived to GitHub Releases, one release per UTC day tagged `archive-YYYY-MM-DD` (the day of the snapshot's `generatedAt`, not marked latest). Each run uploads `heat-<stamp>.json.gz` (the run's `heat.json`, gzipped; `<stamp>` is `generatedAt` without `-` and `:`, for example `heat-20261021T144514Z.json.gz`), about 96 a day. The first run of each UTC day also uploads `cells-<stamp>.tar.gz`, the whole `cells/` directory of that run. Download with `gh release download archive-2026-10-21` or from the Releases page. The step needs the `build` job's `contents: write` permission, and a failed upload never fails the snapshot. Set the repository variable `ARCHIVE` to `false` to turn it off.

## Observers count

`presence/` is an optional Cloudflare Worker with one Durable Object that counts the browser tabs on the site in the last 75 seconds, for the "Observers · N" label (setup, API and privacy in `presence/README.md`); the site reads its URL from the repository variable `PRESENCE_URL` at build time and shows plain "Observers" without it.
The `Presence` workflow (`.github/workflows/presence.yml`) tests and deploys it on manual runs and on pushes to `main` that touch `presence/`, and skips the deploy until the secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` exist.

# Today On Earth

Today On Earth is a news heatmap with no editorial voice: a flat world map that glows where the world's press is writing about something, built from GDELT's free 15-minute Global Knowledge Graph feed. An ingest job (`ingest/`, Node 24 + TypeScript) keeps a rolling 24-hour window of geocoded articles, bins them into H3 resolution-3 cells, and writes the static JSON files described in `docs/DATA-CONTRACT.md` (`heat.json`, `cells/<id>.json`, `history/`); the static site (`web/`) reads only those files. To run the ingest locally: `cd ingest && npm install && npm run ingest` (writes to `ingest/out`; set `COLD_START_HOURS=1` for a quick first run, `OUT_DIR=../web/public/data` to feed the local site, `CARRY_DIR` to keep the carried `state.json.gz` and `history.json.gz` somewhere other than `OUT_DIR`, and `npm test` / `npm run check` to run the unit tests and validate the output against the contract). To run the site: `cd web && npm install && npm run dev`. To deploy on GitHub: make the repository public (scheduled Actions minutes are free there) and set Settings → Pages → Source to "GitHub Actions". A repository variable `SITE_URL` (the site's base URL, for example `https://<user>.github.io/today-on-earth`) is optional and only informational; the workflow does not read it. The `Snapshot` workflow runs every 15 minutes and deploys the rebuilt site.

Place pages: `npm run build` first runs `web/scripts/build-places.mjs` (the `prebuild` step), which reads the snapshot in `web/public/data` and writes a static page for every place with 10 or more articles (`place/<cell id>.html`, no JavaScript) with an Atom feed of its stories beside it (`place/<cell id>.xml`, linked from the page), the index of every place with 2 or more (`places.html`), the day's broadcast as a page (`broadcast.html`, the six signals from `broadcast.json`; six empty slots when the snapshot has none) with its Atom feed (`broadcast.xml`, one entry per UTC day), and `sitemap.xml`, so each deploy carries pages for that snapshot. These files are generated and gitignored; `web/public/robots.txt` (committed) points crawlers at the sitemap. Locally the script runs on whatever `npm run predev` or the ingest put in `web/public/data`; a place whose cell file is missing gets no page and an unlinked index row.

Carried state: the rolling window (`state.json.gz`), the replay history (`history.json.gz`) and the per-cell daily counts behind each cell's normal level `b` (`baseline.json.gz`, last 14 days) travel from run to run through the Actions cache in a repo-root `carry/` folder and are never deployed. After each save the workflow deletes all but the 3 newest `carry-*` cache entries (this needs the workflow's `actions: write` permission; a failed prune never fails the snapshot). A carried file that exists but cannot be read fails the run on purpose, and so does a cache miss unless the repository variable `ALLOW_COLD_START` is `true`. For the first run, set `ALLOW_COLD_START=true`; after the first green run, set it to `false` so a cache outage or evicted entry fails the run instead of shrinking the window (to clear the cache on purpose, set it to `true` for one run). A permitted cold start fetches the last 6 hours of GDELT files and begins a new 24-hour replay history (each run appends one compact heat frame to `history/`, at most 100 frames).

Note: GitHub disables scheduled workflows in public repositories after 60 days without repository activity. Push a commit or run the `Snapshot` workflow manually (Actions → Snapshot → Run workflow) at least every two months, or the map stops updating (do not rely on the keepalive below for this).

Keepalive: GitHub's cron is best-effort, so each snapshot run ends with a `keepalive` job that waits a fixed 780 s and then dispatches the next snapshot unless another snapshot run was created after it (any event, any status) or one is already queued or running. It also dispatches the `Clip` workflow once a day after 00:20 UTC if no clip run exists yet that day. Set the repository variable `KEEPALIVE` to `false` to turn it off.

## Rolling back

The carried files (`state.json.gz`, `history.json.gz`, `baseline.json.gz`) have format versions. Newer code reads older files, but older code cannot read newer ones, so deploying an older commit against a cache written by newer code fails every run, on purpose, rather than silently starting over. To roll back: delete the `carry-*` caches (Actions → Caches, or `gh cache delete` for each `carry-*` key), set the repository variable `ALLOW_COLD_START=true` for one run, then set it back to `false`. That run cold-starts the 6-hour window, and the replay history and the baseline start again from empty.

## Daily clip

Every day at 00:20 UTC (after the 00:15 snapshot) the `Clip` workflow renders a vertical clip of the last 24 hours, about 36 s at 30 fps: a 2 s hook on the first signal's cell, a 1.5 s pull-back, a 7 s time-lapse over the day's replay snapshots, up to three signal cards (each a 1.5 s flight and the card held 5 s) and a 3 s end card, then a 1 s hold. `render/` loads the live site's `clip.html?timeline=1&w=1080&h=1920&fps=30&hook=2&fly=1.5&lapse=7&card=5&end=3&slots=3&max=<n>` once in a headless system Chrome (playwright-core, no browser download), reads the page's plan (`window.__clipPlan()`: the frame count, the clip's UTC day, the poster frame, the segments and the frames where the time-lapse clock crosses a whole hour), and steps it frame by frame (`window.__clipStep(i)`, one screenshot each). `max` is the live `heat.json`'s largest cell count, read once at the start, so the heat scale cannot jump when a deploy lands mid-clip. From the plan it generates the soundtrack (`audio.wav`, 48 kHz mono, deterministic): a low 55/110 Hz sine bed, a click on every whole UTC hour of the time-lapse, a rising glide under the pull-back and each flight, a two-tone blip as each card arrives, a low hit on the hook and the end card, faded in and out. `--music <file>` replaces it with any audio file (looped or trimmed to the clip, faded out over the last 1.5 s) and `--music none` makes a silent clip. ffmpeg encodes `clip-<YYYY-MM-DD>.mp4` (H.264 yuv420p + AAC 128k, faststart, named after the UTC day the time-lapse mostly covers) plus `poster.jpg` of the last time-lapse frame. The flags (`--fps --hook --fly --lapse --card --end --hold --slots`) set the frame rate, the seconds of each part and the number of signal cards. Download the clip from the workflow run's `clip` artifact (kept 30 days) or from the rolling `clips` release on GitHub, where each day's mp4 is added and `poster.jpg` is replaced. Run it by hand with Actions → Clip → Run workflow (width and height are inputs; both must be even). To render locally against the dev server: `cd web && npm run dev`, then `cd render && npm install && npm run clip -- --site http://localhost:5173 --out ../clip-out` (Edge is used on Windows, Chrome elsewhere; `--channel` overrides; without `ffmpeg` on PATH the frames, poster and audio.wav are written, the encode is skipped and the ffmpeg command is logged). In CI, ffmpeg is a pinned, checksum-checked static build (ffmpeg 7.0.2) cached across runs, with apt as the fallback. A page load that fails is retried once; a frame whose step fails is retried once, and a frame that fails twice is replaced by the previous frame; the run fails once more than 10% of frames are bad, or when the page's plan does not match the contract. Posting the clip to TikTok is manual.

## Archive

The site and the carried state only hold the last 24 hours, so every successful snapshot is also archived to GitHub Releases, one release per UTC day tagged `archive-YYYY-MM-DD` (the day of the snapshot's `generatedAt`, not marked latest). Each run uploads `heat-<stamp>.json.gz` (the run's `heat.json`, gzipped; `<stamp>` is `generatedAt` without `-` and `:`, for example `heat-20261021T144514Z.json.gz`), about 96 a day. The first run of each UTC day also uploads `cells-<stamp>.tar.gz`, the whole `cells/` directory of that run. Download with `gh release download archive-2026-10-21` or from the Releases page. The step needs the `build` job's `contents: write` permission, and a failed upload never fails the snapshot. Set the repository variable `ARCHIVE` to `false` to turn it off.

## Observers count

`presence/` is an optional Cloudflare Worker with one Durable Object that counts the browser tabs on the site in the last 75 seconds, for the "Observers · N" label (setup, API and privacy in `presence/README.md`); the site reads its URL from the repository variable `PRESENCE_URL` at build time and shows plain "Observers" without it.
The `Presence` workflow (`.github/workflows/presence.yml`) tests and deploys it on manual runs and on pushes to `main` that touch `presence/`, and skips the deploy until the secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` exist.
